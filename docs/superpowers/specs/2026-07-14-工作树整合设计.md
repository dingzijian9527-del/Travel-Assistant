# 工作树整合设计

## 一、目标

以交付工作树的最新提交作为后续开发的唯一代码整合基线，在不丢失桌面工作树未提交修改的前提下，完成差异处置、验证与可回退的整合准备。

本设计只定义整合边界、差异处置和验收门槛，不执行代码合并，不改变业务行为。

## 二、事实基线

截至二〇二六年七月十四日，桌面工作树的已提交基线是下列提交：

```text
91a2a58
```

交付工作树的最新提交是下列提交，且其历史已包含桌面已提交基线、第一阶段加固工作树和合并稳定工作树：

```text
e1cf409
```

桌面工作树仍有十八个已修改文件和十个未跟踪文件。二十八个文件中，十六个文件与交付工作树内容完全一致，十二个文件存在内容差异。

后端全量测试在桌面工作树与交付工作树均已通过。桌面工作树前端工具测试通过十五项；交付工作树前端工具测试通过十七项。

## 三、整合原则

1. 交付工作树是唯一整合候选；不分别合并合并稳定工作树、第一阶段配置治理工作树或第一阶段强化工作树。
2. 桌面工作树未提交修改必须先完整保留；整合过程不得执行会丢弃修改的版本控制操作。
3. 对内容不同的文件，以交付工作树版本为默认候选；仅在逐项比对证明桌面版本含有未被覆盖的有效行为时，才迁入最小差异。
4. 接口定义、自动生成代码、网关处理器、远程服务实现必须作为一个原子变更组处理，禁止拆散迁移。
5. 每一组变更必须先完成对应测试和接口校验，再进入下一组。

## 四、十二个差异文件的处置清单

### 一）行程更新链路

涉及网关处理器、远程服务处理器与服务层：

```text
api/biz/handler/trip.go
rpc/trip/handler.go
rpc/trip/service.go
```

处置原则：以交付工作树中“行程更新闭环”提交后的版本为准。该版本与接口定义、生成代码、模型、仓储和测试共同演进；桌面版本不得单独覆盖其中任一文件。

验证：创建、列表、最新记录、详情、更新、逻辑删除、跨用户越权访问和无效行程字段均需通过服务与网关测试。

### 二）登录、路由与令牌链路

涉及用户处理器、路由注册和令牌实现：

```text
api/biz/handler/user.go
api/biz/router/register.go
pkg/jwtx/jwt.go
```

处置原则：优先采用交付工作树中已显式标记登录成功与登录失败结果的版本。旧实现仅依据传输状态记录失败次数，而登录业务错误可使用成功传输状态返回，不能满足登录保护要求。

验证：连续错误密码、账号不存在、参数错误、来源地址复用、设备标识复用、登录成功清空计数、访问令牌与刷新令牌类型隔离均须覆盖。

### 三）限流、敏感操作与配置脱敏

涉及通用限流、敏感操作确认和配置摘要：

```text
api/biz/middleware/ratelimit.go
api/biz/middleware/ratelimit_test.go
api/biz/middleware/sensitive.go
pkg/config/mask.go
pkg/config/mask_test.go
```

处置原则：以交付工作树版本为主。桌面版本和交付版本均存在同名但不同内容的实现，必须比较测试所表达的行为，而不是按文件日期覆盖。

补充要求：敏感操作确认能力在整合后必须明确接入实际敏感路由；如果当前不存在密码变更或账户删除接口，应先记录为未接入能力，不能以“代码存在”作为完成结论。

验证：短信、注册、登录、上传和智能体等接口的限流策略应分别验证；配置摘要不得包含令牌密钥、数据库口令、第三方密钥或完整连接信息。

### 四）配置扩展

涉及配置结构：

```text
pkg/config/config.go
```

处置原则：保留交付工作树中与智能体网关、语义检索和令牌刷新有关的完整配置结构，同时检查模板、示例、启动校验、文档与测试是否同步。

验证：开发环境最小配置可启动；非开发环境缺失必填安全字段时启动失败；配置摘要只展示脱敏值。

## 六、分组整合顺序

### 阶段零：保护与对照

1. 记录桌面工作树完整状态和差异文件清单。
2. 为桌面未提交修改建立可恢复备份。
3. 创建独立整合分支，并以交付工作树最新提交为基线。
4. 确认无需单独合并其他工作树。

### 阶段一：账号与运行安全

1. 整合登录失败结果标记、来源地址和设备标识限流。
2. 整合刷新令牌类型校验、配置脱敏和通用限流。
3. 明确敏感操作确认的真实路由接入范围。
4. 补充端到端登录失败限流测试。

### 阶段二：行程契约与更新闭环

1. 整合行程接口定义、生成代码、网关、服务、仓储和测试。
2. 重新生成远程调用代码并校验无额外差异。
3. 验证用户隔离、字段校验与逻辑删除。

### 阶段三：智能体远程流式链路

1. 以交付工作树的远程服务端流式接口为准。
2. 将接口定义、生成代码、网关与智能体服务作为原子组整合。
3. 补充真实服务间流式联调，不以编译通过替代联调通过。

### 阶段四：前端与交付验证

1. 验证前端运行时接口地址、登录刷新、智能体会话与行程更新流程。
2. 执行前端工具测试与浏览器构建。
3. 更新启动、配置、构建和故障排查说明。

## 七、验证门槛

每个阶段完成后均必须执行：

```powershell
go test ./...
node --test src/utils/*.test.mjs
```

在涉及接口定义、远程服务或前端请求地址的阶段，还必须执行：

1. 接口定义重新生成校验；
2. 关键路由请求验证；
3. 智能体流式链路联调；
4. 前端浏览器构建；
5. 敏感值扫描与配置校验。

## 八、回退策略

1. 整合只在独立分支进行，原始桌面工作树和交付工作树保持不动。
2. 每个主题形成独立提交：安全、行程、智能体、前端与交付不得混合。
3. 任一阶段验证失败时，只回退该阶段的独立提交，不影响已验证阶段。
4. 不使用会丢失未提交修改的强制重置或清理操作。

## 九、非目标

本轮整合不新增旅游功能，不重写前端页面，不改变行程领域范围，不引入新的外部基础设施。新增能力必须在整合基线稳定并通过验收后，按后续实施计划单独设计。
