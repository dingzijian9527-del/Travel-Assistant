# 项目代码规范

## 目标

本规则用于约束 Travel Assistant 项目的日常代码开发质量。所有新增和修改代码都必须保持职责清晰、命名明确、错误可追踪、测试可验证，避免出现大函数、大文件、逻辑混杂和跨层调用混乱。

## 通用原则

1. 优先遵循项目已有规则、Kitex/Hertz 官方生成结构和现有代码风格。
2. 代码必须服务当前明确需求，不为了未来假设提前设计复杂抽象。
3. 一个函数只做一件事，一个文件只承载一类职责。
4. 业务逻辑、数据处理、数据持久化、响应转换必须边界清晰。
5. 不允许把鉴权、参数处理、业务编排、数据库访问和响应拼装全部写在同一个函数里。
6. 新增公共能力前，必须先确认是否已有框架能力或项目内已有实现。
7. 对外行为变更必须同步补充或更新测试。

## Go 编码规范

1. 所有 Go 文件必须通过 `gofmt` 或 `go fmt ./...` 格式化。
2. 包名使用小写英文，避免下划线、复数和含糊缩写。
3. 导出类型、函数、常量必须有清晰命名；必要时补充 GoDoc 注释。
4. 变量命名应表达业务含义，禁止使用无意义的 `data`、`tmp`、`obj`、`val` 承载核心业务语义。
5. 错误变量使用 `err`，错误必须及时处理，禁止静默吞掉。
6. 常量集中声明有业务含义的名字，禁止在逻辑中散落魔法数字和魔法字符串。
7. `context.Context` 作为函数参数时必须放在第一个参数位置。
8. 函数参数过多时应使用明确的 request、option 或 config 结构体。
9. 禁止不必要的全局可变状态；确需全局对象时必须说明生命周期和并发安全。
10. 并发代码必须明确退出条件、错误传播、资源释放和 panic 保护。

## 复杂度限制

1. 单个函数建议不超过 50 行。
2. 单个文件建议不超过 300 行。
3. 嵌套层级不得超过 3 层；超过时应通过提前返回、拆分函数或策略分派降低复杂度。
4. 单个函数位置参数不得超过 3 个；超过时优先定义结构体。
5. 圈复杂度明显升高时必须拆分为更小的私有函数。
6. 不允许出现难以测试的大函数；业务核心逻辑必须能被单元测试覆盖。

## 分层职责

1. Handler 只负责请求入口、参数绑定、基础校验、调用业务逻辑和返回结果。
2. Middleware 只负责鉴权、阻断、限流、日志、链路追踪、Recovery 等横切逻辑。
3. Logic 负责业务编排、领域规则判断和调用下层能力，不直接拼 SQL 或封装最终响应。
4. Data 负责纯数据处理，例如清洗、聚合、去重、排序、状态计算，尽量保持无外部副作用。
5. Repository 负责数据库、缓存、外部存储访问，必须隐藏底层存储细节。
6. Converter 负责请求、领域对象、存储对象、IDL response 或 HTTP response 之间的转换。
7. Errors 负责错误定义、错误码映射和对外错误转换，禁止到处硬编码错误消息。

## 错误处理

1. 错误必须带上下文返回，便于定位失败阶段。
2. 禁止直接把底层存储错误、RPC 错误或第三方错误原样暴露给外部用户。
3. 对外错误响应必须经过统一转换，避免泄露内部实现细节。
4. 可重试错误、参数错误、权限错误、资源不存在、系统错误必须区分清楚。
5. 日志中记录内部诊断信息，响应中只返回用户可理解的信息。
6. 禁止使用 panic 处理正常业务错误；panic 仅用于不可恢复的程序错误，并由框架 recovery 兜底。

## 数据访问与安全

1. 数据库访问必须使用参数化查询或 ORM 安全 API，禁止拼接不可信输入。
2. 事务边界必须明确，事务内禁止执行无关耗时操作。
3. 缓存 key 必须有清晰命名规则和过期策略。
4. 不同服务不得直接读写对方私有数据表、缓存 key 或内部存储结构。
5. 敏感信息不得写入源码、日志、错误响应、测试快照或配置样例。
6. 用户输入必须在进入业务逻辑前完成基础校验。

## RPC 与 HTTP 约束

1. RPC 接口以 IDL 为准，变更接口必须先修改 IDL 并重新生成代码。
2. Kitex 生成代码默认不手工修改。
3. HTTP 网关必须使用 Hertz 官方能力处理路由、binding、validator、middleware、render 和 client。
4. Hertz 没有提供的工具或扩展，必须先说明缺口并经用户确认后新增。
5. HTTP handler 不直接访问业务服务私有数据库，必须通过 Kitex RPC client 调用业务服务。
6. 请求和响应字段必须通过 converter 明确转换，禁止在多处散落临时拼装。

## 日志规范

1. 日志必须能帮助定位问题，包含必要的业务标识、请求标识和错误上下文。
2. 禁止在日志中输出密码、token、身份证、手机号完整值等敏感信息。
3. 正常业务分支不滥用 error 级别日志。
4. 高频路径日志要控制体积，避免影响服务性能。
5. 错误日志要保留原始错误链或关键上下文。

## 测试规范

1. 新增业务逻辑必须优先补充单元测试。
2. 共享逻辑、错误处理、边界条件和权限分支必须重点覆盖。
3. 测试断言优先 expected 在前、actual 在后。
4. 测试命名使用 `Test<Function>_<Scenario>`，场景表达清楚。
5. 测试数据只保留当前用例需要的字段，不构造无关大对象。
6. 外部依赖必须 mock、fake 或通过框架测试能力隔离，禁止单元测试依赖真实外部服务。
7. 提交前至少运行与本次改动直接相关的测试；无法运行时必须说明原因。

## 注释规范

1. 文件、接口、核心函数和复杂业务方法必须使用统一注释模板。
2. 注释解释为什么这样做，而不是重复代码表面含义。
3. 复杂业务规则、边界条件、兼容逻辑、临时方案必须写明原因。
4. TODO 必须包含原因、后续动作或触发条件，禁止留下无上下文 TODO。
5. 删除失效注释，禁止代码和注释长期不一致。

统一注释模板：

```go
/*
 * Author： fuyx
 * DataTime： 2026-06-24 11:48:40
 * Desc: 功能简介
 * Body: name -- 用户姓名
 */
```

字段说明：

1. `Author： fuyx`：作者固定为 `fuyx`。
2. `DataTime：`：填写开始编写当前文件、接口、函数或方法的时间，推荐格式为 `YYYY-MM-DD HH:mm:ss`。
3. `Desc:`：填写功能简介，说明该代码块负责什么能力。
4. `Body:`：填写关键入参或请求参数说明；如果是接口，必须列出接收参数，例如 `name -- 用户姓名`。
5. 多个参数时，每个参数单独一行，保持 `参数名 -- 参数含义` 的格式。

## 提交前检查

每次声明完成前至少确认：

1. 代码已格式化。
2. 没有新增无关目录、临时文件、IDE 文件或构建产物。
3. 没有手工修改生成代码。
4. 分层职责没有被破坏。
5. 错误处理、日志和安全边界符合本规则。
6. 已运行相关测试或明确说明未运行原因。
7. 若变更涉及 IDL、路由、框架能力或目录结构，已同步检查 `.codex/rule/kitex-project-rules.md`。
