# Code Review 规则

## 一、提交代码时自动审查

当用户要求提交代码（git commit）时，在执行 commit 之前，对 staged changes 做一次代码审查。

### 审查流程

1. 检查 commit message 格式是否符合 commit-convention.md 规范
2. `git diff --cached` 获取待提交的变更
3. 按下方检查项逐一审查
4. 发现问题 -> 列出问题并给出修复建议，暂停提交等用户确认
5. 无问题 -> 放行，继续执行 commit
6. commit 成功后不得自动执行 `git pull` 或 `git push`。
7. 只有用户明确要求“提交推送”“推送”“提交到仓库”等操作时，才允许执行远程同步或推送。


### 审查原则

- 只审查 staged changes，不审查整个文件
- 问题按严重程度排序：安全漏洞 > 数据泄露 > 逻辑错误 > 性能问题 > 规范问题
- 无问题时不要啰嗦，直接放行

---

## 二、代码合并（自建分支）
- 当用户明确要求推送自建分支时，如果该分支在远程仓库中不存在，则创建远程分支
- 使用自建之分提交后，不允许直接合并到远程主分支
- 自建分支的代码通过代码审核后，仍需用户明确确认，才能合并到主分支

---

## 三、检查项（提交审查）

### 1. 代码规范

- [ ] 检查代码规范是否符合 project-code-style-rules.md 规范
- [ ] 检查项目规范是否符合 kitex-project-rules.md 规范
- [ ] 检查技术栈是否符合 project-tech-stack-rules.md 规范


### 2. 安全检查

- [ ] 敏感操作是否加了分布式锁
- [ ] SQL 是否有注入风险（MyBatis XML 中是否使用 `${}` 拼接用户输入）
- [ ] 是否有硬编码的密钥/密码/Token
- [ ] 用户数据操作是否校验了权限

### 3. 性能检查

- [ ] 是否有 N+1 查询问题
- [ ] 循环内是否有数据库/Redis 操作
- [ ] 大数据量查询是否有分页
- [ ] 是否合理使用缓存

### 4. 业务逻辑检查

- [ ] 边界条件是否处理（null、空集合、0 值）
- [ ] 事务边界是否正确（`Transactional` 范围是否合理）
- [ ] 并发场景是否考虑（分布式锁、乐观锁）

### 5. 数据库变更检查（如有 SQL 文件）

- [ ] DDL 是否有合适的索引
- [ ] 字段类型是否合适，是否有默认值
- [ ] 大表变更是否考虑锁表影响

### 6. gorm 检查

- [ ] db中联查是否使用`join`而非`preload`或者原生sql
- [ ] 分页查询是否使用框架提供的分页机制

## 四、CR 输出格式

```markdown
## CR 结果：<开发分支> -> <目标分支>

### 变更文件
- file1.go (新增/修改/删除)
- file2.go (新增/修改/删除)

### 问题列表
| 级别 | 文件 | 行号 | 问题描述 | 建议 |
|------|------|------|----------|------|
| 🔴 严重 | xxx.go | 42 | 描述 | 建议 |
| 🟡 建议 | xxx.go | 100 | 描述 | 建议 |

### 总结
- 严重问题：X 个
- 建议优化：X 个
- 整体评价：通过/需修改
```
