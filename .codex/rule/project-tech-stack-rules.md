# 项目技术选型规则

## 目标

本规则用于锁定 Travel Assistant 项目的技术栈。后续开发、依赖选择、脚手架生成、环境配置、数据库访问、缓存、消息队列、向量检索和前端实现都必须优先遵循本文件。

## 后端开发语言

1. 后端开发语言固定使用 Golang。
2. Go 版本必须大于 `1.25`，即使用 `1.25+`。
3. 初始化或更新 `go.mod` 时，`go` 指令必须满足 `go 1.25` 或更高版本。
4. 如果本机、CI、部署环境或依赖生态暂时不支持 `1.25+`，必须先提示用户，说明影响和备选方案，经确认后才能调整。
5. 禁止引入 Java、Python、Node.js 等作为后端主业务开发语言；仅允许在明确必要时作为构建、运维或辅助脚本使用。

## 服务端框架

1. RPC 微服务框架固定使用 CloudWeGo Kitex。
2. HTTP 网关框架固定使用 CloudWeGo Hertz。
3. Kitex 与 Hertz 的目录结构、脚手架和框架能力约束，以 `.codex/rule/kitex-project-rules.md` 为准。
4. 禁止使用 Gin、Echo、Fiber、Spring、FastAPI 等框架替代 Hertz 或 Kitex 的职责。

## 数据库

### MySQL

1. 关系型数据库固定使用 MySQL。
2. 结构化业务数据、事务数据、用户数据、订单/行程等强一致业务数据优先存储在 MySQL。
3. 数据库访问必须使用参数化查询或安全 ORM API，禁止拼接不可信输入。
4. Schema、索引、事务边界和迁移方案必须在实现前明确。
5. 跨服务不得直接访问其他服务私有表；需要数据时必须通过对应服务的 RPC 接口获取。

### Milvus

1. 向量数据库固定使用 Milvus。
2. 语义检索、向量召回、Embedding 检索、相似度查询等向量数据场景必须使用 Milvus。
3. Milvus collection、字段、索引类型、metric type、维度、分区策略必须在写入前明确。
4. 业务主数据不得只存 Milvus；Milvus 存储向量和检索元信息，主业务事实数据仍以 MySQL 为准。
5. MySQL 与 Milvus 的数据关联键必须设计清楚，避免无法追踪向量来源。

## 缓存

1. 缓存固定使用 Redis。
2. 热点数据、短期会话、幂等标记、分布式锁、限流计数等缓存场景优先使用 Redis。
3. Redis key 必须有命名规范、业务前缀和过期策略。
4. 禁止把 Redis 当作唯一持久化存储使用。
5. 缓存一致性策略必须明确，包括失效、更新、回源和降级行为。

## 消息队列

1. 消息队列固定使用 Kafka。
2. 异步事件、削峰填谷、跨服务事件通知、日志/行为流式处理等场景优先使用 Kafka。
3. Topic、consumer group、消息 key、重试策略、死信策略和幂等策略必须在实现前明确。
4. 消费者必须保证可重试和幂等，禁止依赖“消息只处理一次”的假设。
5. 消息体结构必须有明确版本或兼容策略，避免生产者和消费者升级互相阻塞。

## 前端技术栈

1. 前端固定使用 UniApp。
2. 多端页面、移动端页面、小程序适配和 H5 入口优先通过 UniApp 实现。
3. 前端不得私自切换为 React、Vue 单体 Web、Flutter、原生小程序或其他框架替代 UniApp。
4. 如果 UniApp 官方能力无法满足某个端能力或插件需求，必须先提示用户，说明限制、备选插件或自定义方案，经确认后才能新增。
5. 前端调用后端必须通过 Hertz 网关暴露的 HTTP API，不直接访问 Kitex RPC 服务。

## 依赖新增规则

1. 新增 MySQL、Milvus、Redis、Kafka、UniApp 相关依赖前，必须优先选择官方 SDK、官方推荐客户端或项目既有封装。
2. 如果需要引入第三方库，必须说明用途、替代方案、维护状态和对项目结构的影响。
3. 禁止引入与本技术选型冲突的替代基础设施，例如 PostgreSQL、MongoDB、RabbitMQ、Pulsar、Elasticsearch 向量主存储等，除非用户明确确认调整技术选型。
4. 依赖版本必须可追踪，不允许使用来源不明或无法维护的包。

## 开发前检查

涉及技术栈的开发开始前必须确认：


1. Go 版本满足 `1.25+`。
2. 使用 Kitex 开发 RPC 服务。
3. 使用 Hertz 开发 HTTP 网关。
4. 结构化数据进入 MySQL。
5. 向量数据进入 Milvus。
6. 缓存能力使用 Redis。
7. 异步消息使用 Kafka。
8. 前端使用 UniApp。
9. 新增依赖或替代方案已经符合本规则；不符合时必须先经用户确认。
