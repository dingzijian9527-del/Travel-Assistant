# 项目工程治理补充规则

## 目标

本规则用于补充 `.codex/rule` 中第二套主规则未完全覆盖的工程治理要求。若本文件与 `kitex-project-rules.md`、`project-code-style-rules.md`、`project-tech-stack-rules.md` 存在冲突，以更严格且更贴合用户明确要求的规则为准。

## IDL 与接口治理

1. 统一使用 Thrift 定义接口，禁止混用 Protobuf。
2. 所有入参、出参、枚举、结构体必须在 `.thrift` 文件内定义。
3. 禁止在 handler、service 或其他业务代码内临时手写结构体承接请求或响应。
4. 接口出入参必须完全依赖 IDL 生成结构。
5. IDL 变更必须留存变更说明。
6. 新增字段默认设置为 optional，避免下游客户端兼容性报错。
7. 删除字段必须经历“注释废弃标识 -> 版本兼容过渡 -> 完全删除”，不能直接移除。
8. 枚举必须注释含义，禁止无注释魔法数字。
9. 公共结构体、通用返回体、分页请求、分页响应应抽公共 IDL，禁止每个服务重复定义。
10. 新增接口、修改字段、删除接口必须同步更新项目 README 接口说明。

## 依赖治理

1. 所有第三方依赖统一在 `go.mod` 声明，禁止手动随意修改 `go.sum`。
2. 引入新第三方包必须评估必要性、维护状态和替代方案。
3. 版本必须锁定明确版本号，不使用 `latest` 等模糊版本。
4. 提交前执行 `go mod tidy`，不允许残留无效依赖。
5. Kitex、Hertz、Netpoll 和基础组件版本全项目统一，禁止多服务同组件多版本不一致。

## 数据库与缓存治理

1. 数据库操作统一封装到 repo 或明确的持久化方法中。
2. 使用 GORM 时禁止忽略错误，每一次数据库操作必须接收并处理 error。
3. 核心查询禁止无约束使用 `SELECT *`，应显式指定字段。
4. Redis Key 统一使用“服务名:业务模块:主键”格式，避免 Key 冲突。
5. 缓存更新策略、过期策略、防击穿、防穿透、防雪崩方案必须在实现前明确。
6. 禁止大量堆积超大 Key 和无过期时间 Key。
7. SQL 必须避免隐式转换、索引失效和无界批量操作。

## 错误码与统一返回

1. 全局定义业务错误码，至少区分系统内部错误、参数错误、权限错误、业务逻辑错误、资源不存在。
2. RPC 返回不允许直接返回原生 error 字符串给调用方。
3. 对外返回结构必须包含 code、msg、data。
4. 内部错误禁止透传数据库、堆栈和敏感实现细节。
5. 调用其他 Kitex 服务时，必须同时判断网络 error 和业务错误码。

## 日志、链路追踪与监控

1. 日志组件必须统一，优先使用 zap 或框架内置日志能力。
2. 生产环境关闭 DEBUG 日志。
3. 每条请求必须透传 traceID 和 spanID。
4. 入参、出参、耗时按需打印，敏感信息必须脱敏。
5. 手机号、身份证、银行卡、密码、令牌和隐私业务数据禁止明文打印。
6. 长报文必须截断，避免日志刷屏。
7. 关键节点必须打日志，包括入参校验、数据库操作、RPC 调用和异常位置。
8. 关键业务需记录耗时、异常计数、QPS 等监控指标。

## 配置与敏感信息

1. 数据库、Redis、Kafka、RPC 地址、超时、限流开关等配置必须放入配置文件、环境变量或配置中心。
2. 禁止在代码中硬编码 IP、端口、密码、密钥和环境差异配置。
3. 配置区分 dev、test、prod，通过环境变量或配置中心选择加载。
4. 敏感配置禁止提交 Git，仓库只保留配置模板。
5. 配置读取逻辑统一封装初始化，不允许多处重复解析配置文件。

## 外部调用与消息队列

1. Kafka 生产者、消费者客户端必须统一初始化，不允许动态频繁创建销毁。
2. 消息消费必须做好幂等设计，避免重复消费导致数据错乱。
3. 消费失败必须区分重试、忽略、告警和死信策略。
4. 外部 Kitex 服务调用必须设置超时、熔断和重试策略。
5. 外部三方接口必须统一封装客户端，并具备超时、异常捕获和降级兜底逻辑。

## AI 生成代码约束

1. AI 生成代码后必须人工逐行审查，不能直接提交入库。
2. 审查重点包括分层是否越层、SQL 是否合理、错误是否处理、资源是否泄漏、目录是否合规。
3. AI 自动生成的冗余注释、无用打印、无效变量必须清理。
4. AI 生成 IDL 和 Kitex 代码后，必须人工校验是否符合 IDL 规范，确认 `kitex_gen` 路径正确且生成代码未被私自改动。
5. AI 新增目录和文件前，必须先校验是否在允许目录清单内。
6. AI 补全逻辑必须保证函数单一职责，禁止一次性堆砌超大函数。
7. AI 生成错误捕获逻辑必须完整，禁止遗漏 error 接收和判断。

## 超时、限流、熔断与并发安全

1. 所有 RPC 调用、数据库查询、Redis 操作必须设置合理超时。
2. 共享变量和并发修改数据必须加锁或使用原子操作。
3. 禁止无保护的全局并发修改。
4. 接口入口必须配置限流策略。
5. 下游依赖故障必须配置熔断和降级策略，避免雪崩。

## 版本迭代与废弃治理

1. 接口字段、旧接口下线必须经历“注释废弃标识 -> 版本兼容过渡 -> 完全删除”三步。
2. 废弃代码、无用常量、未使用结构体必须及时清理。
3. 长期遗留问题必须登记整改计划，禁止无限期堆积。

## 企业级工程化拆分补充规则

1. 网关层继续以 Hertz 官方脚手架结构为准，所有 HTTP 请求参数绑定、基础参数校验、路由注册、中间件挂载必须放在 `api/` 内完成。
2. `api/biz/handler/` 只负责接收请求、调用校验、编排网关 service 或 RPC client、返回 HTTP 响应，禁止写持久化和复杂业务规则。
3. `api/biz/middleware/` 专门承载鉴权、阻断、请求编号、访问日志、异常恢复、限流、跨域等横切逻辑，禁止把中间件逻辑散落到 handler。
4. `api/biz/validator/` 专门承载 Hertz 请求参数校验辅助方法，禁止在 handler 中重复堆砌相同校验代码。
5. `api/biz/utils/upload/` 只作为网关上传场景的调用适配层，实际可复用上传校验和存储能力必须沉淀到 `pkg/uploadx`。
6. `conf/` 是项目统一配置目录，只允许提交无敏感信息的 `config.yaml` 示例和 `config.yaml.tpl` 模板；生产密码、密钥、令牌必须通过环境变量或配置中心注入。
7. 配置读取统一使用 `pkg/config` 封装的 Viper 加载能力，禁止在业务代码中重复创建 Viper 实例解析 YAML。
8. 日志统一使用 `pkg/logger` 封装的 Zap 日志组件，日志目录、日志级别、保留天数从 `conf` 读取；默认只保留最近 7 天日志，启动时自动清理过期日志。
9. `pkg/bootstrap` 是进程启动初始化入口，所有需要提前加载的配置、日志、基础工具必须在 `main` 中通过 bootstrap 初始化；允许使用 `init` 函数注册默认配置路径，但禁止在 init 中偷偷连接数据库、Redis、MQ 或外部服务。
10. 工具类统一放在 `pkg/<name>x` 命名空间中，例如 `pkg/uploadx`；工具包只能提供通用能力，禁止依赖具体业务服务内部实现。
11. RPC 服务的启动入口统一放在 `cmd/<service>/main.go`，脚手架生成的 `rpc/<service>/main.go` 需要移动到 `cmd/<service>/main.go`；`rpc/<service>/` 只保留业务实现、`service.go`、`model.go`、`repo.go`、`dto.go`、`errors.go` 等文件。
12. 所有新入口必须支持通过配置文件和环境变量调整端口、超时、日志级别、上传限制等运行参数，禁止硬编码运行环境差异。
13. 新增第三方依赖必须写入 `go.mod` 固定版本，并在交付前执行 `go mod tidy`、`go test ./...` 或说明无法执行的原因。
